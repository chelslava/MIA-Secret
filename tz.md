## Локальный менеджер секретов **MIA Secret** на Rust с конфигурационным файлом, API и CLI

## 1. Общие сведения

### 1.1. Назначение системы

Разработать локальное приложение на **Rust**, предназначенное для защищённого хранения секретов и предоставляющее два интерфейса доступа:

- **CLI** для работы пользователя из командной строки;
- **локальный HTTP API** для доступа из других приложений.

Приложение не должно содержать графический интерфейс.

Система должна работать как локальный сервис и использовать файловое хранилище и конфигурационный файл.

### 1.2. Основные цели

Система должна обеспечивать:

- безопасное локальное хранение секретов;
- шифрование чувствительных данных;
- централизованную настройку через конфигурационный файл;
- локальный токенизированный API;
- единый набор бизнес-правил для CLI и API;
- переносимость между Windows и Linux, при возможности — macOS.

### 1.3. Основные ограничения

- реализация только на **Rust**;
- без GUI;
- без зависимости от .NET;
- без внешнего сервера БД;
- без внешнего сетевого доступа;
- сервис должен слушать только loopback-интерфейс.

---

## 2. Технологические требования

### 2.1. Язык и платформа

Обязательные требования:

- язык: **Rust stable**;
- сборка через `cargo`;
- поддерживаемые ОС:
    - Windows;
    - Linux;
    - опционально macOS.

### 2.2. Рекомендуемый стек

Рекомендуется использовать следующий стек:

- **CLI**: `clap`
- **API**: `axum`
- **Async runtime**: `tokio`
- **Сериализация**: `serde`, `serde_json`
- **Конфигурация**: `toml`, `serde`, `config` или аналогичный crate
- **База данных**: `SQLite` через `sqlx` или `rusqlite`
- **Шифрование**: `aes-gcm`
- **KDF**: `argon2`
- **HKDF**: `hkdf`
- **Хеширование токенов**: `argon2` или `sha2`/`hmac` по утверждённой модели
- **Zeroization**: `zeroize`
- **Логирование**: `tracing`, `tracing-subscriber`
- **UUID**: `uuid`
- **Дата и время**: `time` или `chrono`

### 2.3. Обоснование подхода

В качестве архитектурного ориентира допускается использовать идеи Rust-проекта `passman`:

TOML-конфигурация, Argon2 для derivation, AES-256-GCM для шифрования, единый локальный vault-подход, отдельные CLI-команды для управления настройками. Однако в рамках данного проекта GUI не требуется, а вместо него должен быть реализован локальный API. ([GitHub](https://github.com/0M3REXE/passman/tree/main))

## 3. Режимы работы

Приложение должно поддерживать два режима.

### 3.1. Режим сервиса

Запуск локального сервиса:

```bash
mia-secret serve
```

Функции режима:

- запуск HTTP API;
- чтение конфигурационного файла;
- инициализация БД;
- загрузка криптографических параметров;
- обработка запросов;
- проверка и применение токенов;
- корректное завершение по системным сигналам.

### 3.2. Режим CLI

Запуск команд:

```bash
mia-secret <command> [options]
```

CLI должен:

- работать через локальный API как основной способ взаимодействия;
- при необходимости поддерживать внутренний fallback-режим через общие сервисы;
- не дублировать бизнес-логику API.

## 4. Архитектура приложения

### 4.1. Основные модули

Приложение должно быть разделено на следующие логические части:

- **domain** — доменные сущности и правила;
- **application** — сценарии использования;
- **infrastructure** — БД, конфиг, шифрование, файловая система;
- **api** — HTTP-маршруты, middleware, DTO;
- **cli** — команды командной строки;
- **config** — загрузка, валидация и применение конфигурации.

### 4.2. Архитектурные требования

- CLI и API используют один и тот же слой бизнес-логики;
- конфигурация загружается централизованно;
- криптография инкапсулируется в отдельном сервисе;
- доступ к данным реализуется через репозитории или сервисы хранения;
- все чувствительные операции должны быть тестируемыми отдельно.

## 5. Конфигурационный файл

### 5.1. Обязательность конфигурации

Приложение **обязательно должно использовать конфигурационный файл** для настройки поведения сервиса и CLI.

Конфигурационный файл является основным способом настройки приложения.

Дополнительно допускается переопределение значений через:

- переменные окружения;
- аргументы CLI.

### 5.2. Формат конфигурации

Основной формат конфигурации: **TOML**.

Пример имени файла:

```
mia-secret.toml
```

Выбор TOML обоснован тем, что подобный подход уже хорошо зарекомендован в Rust-приложениях, в том числе в `passman`, где конфигурация хранится в TOML и включает отдельные секции для безопасности, логирования, бэкапов и параметров генерации. ([GitHub](https://github.com/0M3REXE/passman/tree/main))

### 5.3. Расположение конфигурационного файла

Рекомендуемые пути:

- **Windows**: `%APPDATA%\mia-secret\mia-secret.toml`
- **Linux**: `~/.config/mia-secret/mia-secret.toml`
- **Fallback**: `./mia-secret.toml` в рабочем каталоге

### 5.4. Приоритет источников конфигурации

Приоритет должен быть следующим:

1. аргументы командной строки;
2. переменные окружения;
3. конфигурационный файл;
4. значения по умолчанию.

### 5.5. Структура конфигурации

Конфиг должен быть разбит по секциям.

Пример структуры:

```toml
[general]
data_dir = "./data"
database_path = "./data/secrets.db"
log_level = "info"
enable_file_logging = true

[server]
host = "127.0.0.1"
port = 3765
request_timeout_secs = 30

[security]
token_header = "Authorization"
lock_timeout_secs = 300
max_failed_attempts = 5
min_master_password_length = 12

[crypto]
argon2_memory_kb = 65536
argon2_time_cost = 3
argon2_parallelism = 4
encrypt_notes = true
encrypt_custom_fields = true

[storage]
auto_migrate = true
create_backup_before_write = true
max_backups = 10

[cli]
output_format = "table"
interactive = true
```

### 5.6. Требования к конфигурации

Конфигурация должна позволять настраивать:

- путь к каталогу данных;
- путь к БД;
- адрес и порт локального API;
- уровень логирования;
- параметры Argon2;
- таймаут блокировки;
- число неудачных попыток;
- режимы резервного копирования;
- формат вывода CLI;
- криптографические флаги;
- поведение инициализации.

### 5.7. Команды управления конфигурацией

CLI должен поддерживать команды:

```bash
mia-secret config show
mia-secret config validate
mia-secret config init
```

Опционально:

```bash
mia-secret config set server.port 3765
mia-secret config reset
```

`config init` должен создавать файл конфигурации по умолчанию, если он отсутствует.


## 7. Хранилище данных

### 7.1. Тип хранилища

Поскольку проект должен быть реализован только на Rust, вместо LiteDB необходимо использовать **SQLite** как нативную локальную файловую БД.

### 7.2. Файлы приложения

Приложение должно использовать как минимум следующие файлы:

- `secrets.db` — SQLite база;
- `master.key` — мастер-ключ или защищённый ключевой материал;
- `mia-secret.toml` — конфигурационный файл;
- каталог резервных копий — при включённой политике backup.

### 7.3. Инициализация

При первом запуске приложение должно:

- создать каталог данных;
- создать конфиг, если он отсутствует;
- создать БД;
- применить миграции;
- создать ключевой материал.

## 9. Шифрование и защита данных

### 9.1. Алгоритмы

Система должна использовать:

- **AES-256-GCM** для шифрования данных;
- **Argon2id** для derivation ключей;
- при необходимости **HKDF-SHA256** для разделения ключевого материала;
- zeroization для чувствительных значений в памяти.

Подобные практики применяются и в `passman`: AES-256-GCM, Argon2id, HMAC-SHA256, HKDF и zeroization. Для данного проекта этот подход допустимо использовать как ориентир, но без GUI-компонента. ([GitHub](https://github.com/0M3REXE/passman/tree/main))

### 9.2. Требования к шифрованию

- уникальный nonce на каждую запись;
- пароль хранится только в зашифрованном виде;
- заметки и custom fields шифруются по настройке или всегда;
- ключи и расшифрованные данные не логируются;
- чувствительные буферы должны по возможности очищаться из памяти.

### 9.3. Хранение ключа

Ключевой файл должен:

- храниться локально;
- быть доступен только текущему пользователю;
- создаваться с ограниченными правами доступа;
- не выводиться через API и CLI.

## 10. Аутентификация и авторизация

### 10.1. Тип

API должен использовать **Bearer Token**:

```
Authorization: Bearer <token>
```

### 10.2. Требования

- токен показывается только при создании;
- в базе хранится только хеш токена;
- токен должен поддерживать scopes;
- проверка срока действия обязательна, если токен ограничен по времени.

### 10.3. Scopes

Минимально обязательные scopes:

- `secrets.read`
- `secrets.write`
- `tokens.manage`

Дополнительно допустимы:

- `secrets.delete`
- `secrets.list`
- `config.read`
- `service.health`

## 11. REST API

### 11.1. Базовый путь

```
/api/v1
```

### 11.2. Методы для секретов

- `POST /api/v1/secrets`
- `GET /api/v1/secrets`
- `GET /api/v1/secrets/{id}`
- `GET /api/v1/secrets/by-path/{path}`
- `PATCH /api/v1/secrets/{id}`
- `DELETE /api/v1/secrets/{id}`

### 11.3. Методы для токенов

- `POST /api/v1/tokens`
- `GET /api/v1/tokens`
- `POST /api/v1/tokens/{id}/revoke`

### 11.4. Методы для конфигурации

Если будет разрешён доступ к конфигурации через API, то только в безопасном режиме и без чувствительных полей.

Минимально допустимо:

- `GET /api/v1/config` — только чтение безопасной части конфигурации

Лучше ограничить управление конфигурацией только CLI.

### 11.5. Health

- `GET /api/v1/health`

Ответ должен содержать:

- статус;
- версию;
- доступность БД;
- признак загрузки конфигурации.

## 13. Валидация

- `path` обязателен;
- `path` уникален;
- пароль обязателен при создании секрета;
- пустые строки после trim запрещены;
- строки конфигурации должны валидироваться при запуске;
- Argon2-параметры должны иметь безопасный нижний порог.

---

## 14. Формат ошибок

Все ошибки API должны возвращаться в формате:

```json
{
  "error": {
    "code": "validation_error",
    "message": "Описание ошибки",
    "traceId": "..."
  }
}
```

Категории ошибок:

- `validation_error`
- `not_found`
- `conflict`
- `unauthorized`
- `forbidden`
- `crypto_error`
- `config_error`
- `storage_error`
- `internal_error`

## 15. Логирование

Запрещено логировать:

- пароли;
- токены;
- мастер-ключ;
- расшифрованные секреты;
- сырой конфиг с чувствительными параметрами.

Разрешено логировать:

- технические ошибки;
- события запуска;
- маршрут API;
- статус кода;
- trace id;
- факт загрузки конфигурации без её секретного содержимого.

## 16. Нефункциональные требования

- приложение должно работать как единый бинарник;
- запускаться как CLI и как сервис;
- использовать конфигурационный файл как основной источник настроек;
- поддерживать автоматическую инициализацию;
- типовые операции чтения должны укладываться в целевой интервал до 300 мс;
- завершение сервиса должно быть корректным;
- запись в БД должна быть транзакционной;
- конфигурация должна валидироваться на старте.

---

## 17. Критерии приёмки

Система считается принятой, если:

1. проект полностью реализован на Rust;
2. приложение использует TOML-конфиг;
3. конфиг создаётся и валидируется;
4. сервис работает только локально;
5. API доступен;
6. CLI полностью работает;
7. секреты шифруются;
8. токены работают корректно;
9. чувствительные данные не пишутся в логи;
10. конфигурация управляет параметрами сервиса и безопасности.
